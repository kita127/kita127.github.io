## 単体テスト野郎

私は単体テスト野郎です。実装時にはほとんどの場合において TDD、テストファースを意識してプログラミングします。
Kent Beck の「テスト駆動開発」を読んでから数年間、このスタンスで仕事をしています。
単体テストを書くことは、それにかかるコストを上回るメリットがたくさんあると、実務の中でのたくさん経験してきました。

現在の職場は単体テストに対するリテラシーは比較的高く、全員がある程度、実装時にはテストを追加します。
そんな職場の中でも私のテストに対するこだわりは異質で、恐らく同僚は私の偏執を理解できないと思います。
それはテストを書く動機が私と同僚とでは異なっており、異質の原因はその動機の違いだと考えています。

同僚と話をする中で他の皆がテストを書く一番の動機はリグレッション(デグレード)に対する防衛のようです。
もちろん、私もリグレッション対策が単体テストを書く一つの動機ではあります。
単体テストを積み重ねることで、機能追加や拡張時のリグレッションを防いでくれることは明白な単体テストの利点です。

しかし、私はこの利点と同じかそれ以上に単体テストによる別の利点があると実感しています。

***テストを書くと圧倒的に設計が良くなる！！！！***

これが私が信じる単体テストにおける利点のもう一つの側面です。

これを同僚との話の中で話題に挙げるのですが、なかなか伝わりません。
かと言ってこの利点をしっかり説こうと思っても、一言で表せないためなかなか職場の雑談では伝えきれません。
いつも「テストを書くと設計も良くなりますよね！」とだけ言って、「何を言っているんだ、こいつは？」という間をいただきます。

## 単体テストによりなぜ設計が良くなるのか？

### 前提 : テストファースト

それでは想いを綴っていきます。ですが、このテストによって設計が良くなる理論にはひとつ大前提があります。
それは必ず「TDD」あるいは「テストファースト」で実装を進めることです。

これはよくよく考えると当然で、後でテストを書くということは、すでにプロダクトコードが完成しているということなのでテストが設計の改善に影響しないからです。
一応、テストを書いてからリファクタするという選択肢もありますが、ここがまたテストファースとでやった場合と状況が異なってきます。
なぜなら後書きテストで実装した場合は、プロダクトコードもテストコード自体もテストファーストで取り組んだ場合よりも変更が難しくなります。
この理由も詳しく後ほど書きます。

以上により、今回語る「単体テストにより設計が良くなる」理論はプロダクトコードの実装よりも先にテストコードを書くことを前提に説明します。

## なんで良くなるの？ 理由 : テストを書きやすくしようとするから

これからあなたは開発しているシステムのある機能を実装していきます。テストファースで進めるため、まずはプロダクトコードの前にそのコードをテストするためのコードから書きます。

当然複雑なものは書きたくないため、テストのための準備(Arrange)も実行(Act)も検証(Asesrt)もシンプルでわかりやすく書こうとします。
すると当然ながら、テスト対象のクラス(System under test)はテストをしやすいように作ろうという意識になります。

テストをしやすいクラスは設計の良いクラスになります。以上が良くなる理由です。

と言っても「なぜ良くなるの？」を説明していないため、ここをさらに深堀りしていきます。

### 理由その1 : 疎結合なクラスになる

テストをしやすくしようと思った場合、なるべくテスト対象クラスは独立して機能するようします。
テストするためにテスト対象クラス以外のクラスやモジュールがたくさん必要となると、当然テストするための準備(Arrange)が大変になります。
なるべく、テスト対象クラスが必要とする依存を減らした結果、自然、疎結合なクラスになります。
ご存知の通り、クラス設計は高凝集、疎結合が良いとされています。テストをシンプルに書こうとした結果、自然と結合度が優れたクラスになります。

### 理由その2 : 入出力を簡潔にする

テストの大まかな流れは、テスト対象のクラス、メソッドに入力を与え、出力結果が期待値と一致することを確認します。
テストを簡潔にしようとした場合、この「入力値の組み立て」、「テスト対象への入力の与え方」、「期待値の組み立てやすさ」が重要になります。
つまり、以下のようなテストは書きたくないはずです。

- テスト対象に与える入力値の生成が大変
  - たくさんのデータが必要
  - たくさんのデータの複雑な連携が必要
- テスト対象の事前組み立てが大変
  - テストするための事前のDB設定など実行前の準備が複雑
  - テスト対象をテストするための設定値などが複雑
- 期待値の算出が容易ではない
  - テスト対象が副作用のある処理を含むため、実行環境により出力結果が変化する
    - グローバル変数
    - 日付
    - 乱数
    - I/O

その結果、テスト対象クラスは自然、複雑な事前設定がなく、かつ、入力によって一意に出力が決まる設計になります。
このいついかなる時も、入力によって一意に出力が定まる特性を「参照透過性」といいます。
参照透過な処理は副作用やグローバルな状態を持たないため、可読性に優れ、また、同じ理由から並列処理などとも相性がいいです。
この「参照透過性」もプログラミングの設計においては良いとされる指標のひとつです。

オブジェクト指向で設計した場合は、オブジェクトの状態なども計算時の入力の一部となるため、
純粋にメソッドの引数のみで出力結果が一意に決まるわけではないですが、それでも参照透過に近い設計のほうがテストも書きやすいため、
オブジェクトの状態をイミュータブルにしたり、なるべく関連する状態の数は減らそうとしたりなど、やはり良いプラクティスで実装する意識が働きます。

このように、テストを事前に書くことにより、テスト対象クラス、メソッドの入出力のフローを簡潔にし、かつ、自然に参照透過よりの設計をするようになります。

### 理由その3 : 副作用を分離する

「入出力を簡潔にする」でも触れていますが、テストを書きやすくしようとした場合、必ず副作用を分離しようとします。
その前にプログラミングにおける副作用について私の理解を説明します。

処理が自分の内側や引数で与えられた入力以外に外部から影響を受けたり、あるいは外部に影響を与えることを副作用と呼びます。
具体的には以下が副作用の一例です。

- グローバル変数を参照・更新する
- ファイルを読み書きする
- データベースを読み書きする
- 外部と通信する
- 乱数や日付などの実行時タイミングごとに変化する値の参照
- 引数で渡されたオブジェクトの状態を変更する

これら副作用をテスト対象に持ち込むと著しくテストがしづらい、もしくはできなくなります。

とはいえ、当然ながら全く外部と通信しなかったり、I/Oが扱えないと実用的なアプリケーションにはならないため、これらを完全になくすことはできません。
大切なのはロジックと副作用を区別することです。

テスト対象は主に、複雑なドメインやビジネスの関心を扱うロジックのはずです。
これらは副作用と切り離して、テスト容易にすべきです。

テストを書いた場合、テストでは扱いづらい副作用を切り離すため、自然と純粋な処理と副作用を分離した設計に寄っていきます。

### まとめ

これまでに述べた理由により、事前にテストを書くことにより自然と設計自体が良い方向に向かうようになります。
この設計が良くなる＋リグレッションを防止する効果により、私は積極的に TDD を用います。

## おまけ : テストを信頼できるドキュメントにしよう！

事前にテストを書くと自然、可読性の高いテストを書くようになります。冒頭でも述べた通り、テストフローの構成としては、
「テストデータの準備(Arrange)」、「テストの実行(Act)」、「テスト結果の検証(Assert)」の3段階で構成されていますが、これらをシンプルに書くようになります。

これを推し進めると、1つ1つのテストが簡潔な仕様書になります。
私はこれを突き詰めていけないかと考えています。

私は設計書、ドキュメントの類いが基本的に嫌いです。なぜ、嫌いかと言うとよく嘘をつくからです。
はじめはプログラムと整合が取れていても時が経つにつれ、不具合修正や新機能を織り込み忘れ、実態と乖離していきます。
結果、ドキュメントを信用できなくなり、読まれず、放置されるようになります。

しかし、テストは嘘をつきません。仮にテストが嘘をついていたら結果がレッドになって気づけます。
結果的にテストこそが最も信頼できるドキュメントになり得ます。

テストを書く習慣ができ、テストにより設計が洗練されるようになってきたならば、
次に目指すべきはテストのドキュメント化ではないかと私は思います。
