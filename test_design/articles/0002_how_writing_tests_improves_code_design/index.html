テスト／設計研究所

テストのために書いているんじゃあない！設計のために書いているんだ！

私は単体テスト野郎

私は単体テスト野郎です。実装時にはほとんどの場合においてテストファーストを意識してプログラミングします。 Kent Beck の「テスト駆動開発」を読んでから数年間、このスタンスで仕事をしています。 単体テストを書くことには、それにかかるコストを上回るメリットがたくさんあると、実務の中で実感してきました。

現在の職場は単体テストに対するリテラシーは比較的高く、全員が、実装時にはある程度テストを追加します。 そんな職場の中でも私のテストに対するこだわりは異質で、おそらく同僚は私の偏執を理解できないと思います。 それはテストを書く動機が私と同僚とでは異なっており、異質の原因はその動機の違いだと私は考えています。

同僚と話をする中で他の皆がテストを書く一番の動機はリグレッション（デグレード）に対する防衛のようです。 もちろん、私もリグレッション対策が単体テストを書く一つの動機ではあります。 単体テストを積み重ねることで、機能追加や拡張時のリグレッションを防いでくれることは明白な単体テストの利点です。

しかし、私はこの利点と同じかそれ以上に単体テストによる別の利点があると実感しています。

テストを書くと圧倒的に設計が良くなる！！！！

これが私が信じる単体テストにおける利点のもう一つの側面です。

これを同僚との話の中で話題に挙げるのですが、なかなか伝わりません。 かと言ってこの利点をしっかり説こうと思っても、一言で表せないためなかなか職場の雑談では伝えきれません。 いつも「テストを書くと設計も良くなりますよね！」とだけ言って、「何を言っているんだ、こいつは？」という間をいただきます。

今回はこのいつも一言で言い表せない想いを、このブログに綴っていこうと思います。伝われぇ！！

単体テストによりなぜ設計が良くなるのか？

前提: テストファースト

それでは想いを綴っていきます。ですが、このテストによって設計が良くなる理論にはひとつ大前提があります。 それは必ず「テストファースト」で実装を進めることです。

これはよくよく考えると当然で、後でテストを書くということは、すでにプロダクトコードが完成しているため、テストが設計の改善に影響しにくいからです。 一応、テストを書いてからリファクタするという選択肢もありますが、ここがまたテストファーストで進めた場合と状況が異なってきます。 なぜなら後書きテストで実装した場合は、プロダクトコードもテストコード自体もテストファーストで取り組んだ場合よりも変更が難しくなる傾向があります。 なぜならこの後説明する、テストファーストによる設計向上の恩恵を受けにくく、結果としてリファクタしにくい作りになりやすいからです。

以上により、今回語る「単体テストにより設計が良くなる」理論はプロダクトコードの実装よりも先にテストコードを書くことを前提に説明します。

なんで良くなるの？ それはテストを書きやすくしようとするから！

これからあなたは開発しているシステムのある機能を実装していきます。テストファーストで進めるため、まずはプロダクトコードの前にそのコードをテストするためのコードから書きます。

当然複雑なテストは書きたくないため、テストのための準備（Arrange）も実行（Act）も検証（Assert）もシンプルでわかりやすく書こうとします。 すると当然ながら、テスト対象のクラスはテストをしやすいように作ろうという意識になります。

テストをしやすいクラスは設計の良いクラスになる傾向があります。以上が良くなる理由です。

と言っても「なぜ良くなるの？」を説明していないため、ここをさらに深掘りしていきます。

理由その1: 疎結合なクラスになる

テストをしやすくしようと思った場合、なるべくテスト対象クラスは独立して機能するようにします。 テストするためにテスト対象クラス以外のクラスやモジュールがたくさん必要となると、当然テストするための準備（Arrange）が大変になります。 なるべくテスト対象クラスが必要とする依存を減らすことで、自然に疎結合なクラスになります。 ご存知の通り、クラス設計は高凝集、疎結合が良いとされています。テストをシンプルに書こうとした結果、自然と結合度の低いクラスになります。

理由その2: 入出力を簡潔にする

テストの大まかな流れは、テスト対象のクラスやメソッドに入力を与え、出力結果が期待値と一致することを確認します。 テストを簡潔にしようとした場合、この「入力値の組み立て」、「テスト対象への入力の与え方」、「期待値の組み立てやすさ」が重要になります。 つまり、以下のようなテストは書きたくないはずです。

  • テスト対象に与える入力値の生成が大変
  • たくさんのデータが必要
  • たくさんのデータの複雑な連携が必要
  • テスト対象の準備が大変
  • テストするために必要となるDB設定など実行前の準備が複雑
  • テスト対象をテストするための設定値などが複雑
  • 期待値の算出が容易ではない
  • テスト対象に以下のような副作用を含むため、実行タイミングにより出力結果が変化する
    • グローバル変数
    • 日付
    • 乱数
    • I/O

その結果、テスト対象クラスは、複雑な事前設定がなく、かつ、入力によって一意に出力が決まる設計にしようとします。 このような純粋な処理は副作用やグローバルな状態を持たないため、処理の把握がしやすく、可読性・保守性に優れます。

オブジェクト指向で設計した場合は、オブジェクトの状態なども計算時の入力の一部となるため、 メソッドの引数のみで出力結果が一意に決まるわけではないですが、それでも副作用のない純粋に近い設計のほうがテストも書きやすいため、 オブジェクトの状態をイミュータブルにしたり、なるべく関連する状態の数は減らそうとしたりなど、やはり良いプラクティスで実装する意識が働きます。

このように、テストを事前に書くことにより、テスト対象クラス、メソッドの入出力のフローを簡潔にし、かつ、自然に純粋な設計をするようになります。

理由その3: 副作用を分離する

理由その3「入出力を簡潔にする」でも触れていますが、テストを書きやすくしようとした場合、副作用を分離しようとする意識が働きます。 その前にプログラミングにおける副作用について私の理解を説明しておきます。

処理が自分の内側や引数で与えられた入力以外に外部から影響を受けたり、あるいは戻り値以外に外部に影響を与えることを副作用と呼びます。 具体的には以下が副作用の一例です。

  • グローバル変数を参照・更新する
  • ファイルを読み書きする
  • データベースを読み書きする
  • 外部と通信する
  • 乱数や日付などの実行時タイミングごとに変化する値の参照
  • 引数で渡されたオブジェクトの状態を変更する

これらの副作用をテスト対象に持ち込むと、テストが著しくしづらくなり、場合によってはテストできなくなります。

とはいえ、当然ながら外部とまったく通信しなかったり、I/Oを扱えなかったりすると実用的なアプリケーションにはならないため、これらを完全になくすことはできません。 大切なのはロジックと副作用を分離することです。

テスト対象は主に、複雑なドメインやビジネス上の関心を扱うロジックのはずです。 これらは副作用と切り離して、テストを容易にすべきです。

テストファーストで書いた場合、テストでは扱いづらい副作用を切り離すため、自然と純粋な処理と副作用を分離した設計に寄っていきます。

まとめ

これまでに述べた理由により、事前にテストを書くことにより自然と設計自体が良い方向に向かうようになります。 設計を改善し、リグレッションを防止できるという効果があるため、私は積極的にテストファーストを用います。

おまけ: テストを信頼できるドキュメントにしよう！

事前にテストを書くと、自然に可読性の高いテストを書く意識が働きます。

これを推し進めると、1つ1つのテストが簡潔な仕様書になります。 私はこれを突き詰めていきたいと考えています。

私は設計書、ドキュメントの類いが基本的に嫌いです。なぜ嫌いかというと、よく嘘をつくからです。 はじめはプログラムと整合が取れていても、時がたつにつれて、不具合修正や新機能をドキュメントに織り込むことを忘れ、プログラムと乖離していきます。 結果、ドキュメントを信用できなくなり、しまいには読まれず、放置されるようになります。

しかし、テストは嘘をつきません。もちろん、テスト自体に誤りがあることはあります。 それでも、テストと実装の前提が変わったときには、結果の変化として気づくきっかけを得られます。 結果的にテストは信頼できるドキュメントになり得ます。

アプリケーションの寿命が延びた昨今では、自動テストを書くことが比較的当たり前になってきたかと思います。 テストを書く習慣ができ、テストにより設計が洗練されるようになってきたならば、 次に目指すべきはテストのドキュメント化ではないかと私は思います。

言い訳

「テストファーストで書けば良い設計になる」と断定的に書いていますが、もちろん後からテストを書いても良い設計はできますし、 テストファーストで書いたからと言って、必ずしも良い設計になるとは限りません。 例えば、テストのためだけに本来は不要な I/F を用意したり、不要な抽象化をしたりする場合もあります。

なので、テストファーストと言っても、主役はプロダクトコードであり、テストコードはサポートという意識がないと、 テストのための設計という本末転倒な結果にもなり得ます。過ぎたるは猶及ばざるが如しですね。

結局のところ、本当に良い設計ができるかは設計者本人の設計スキルに依るでしょう。

記事本文ではテストファーストは良い設計になると強めに書きましたが、テストファーストは設計を良くする示唆を与えてくれるくらいで、 テストファーストにしただけでは劇的に設計は良くはならないでしょう。身も蓋もない事を言うと良い設計をしようと思ったら、結局、設計の勉強も必要ということですね.... ですが今回は想いを伝えることが主目的でしたので、割と強めに記事を書きました。
